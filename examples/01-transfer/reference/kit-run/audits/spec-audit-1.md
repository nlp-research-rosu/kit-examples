# Spec audit 1 — `transfer(address,uint256)` (same-agent inline review)

**Mode:** inline fallback (same-agent review, per `using-kit`). Recorded as such;
not independent review. Audited strictly from the on-disk artifacts:
`inputs/spec.k`, `inputs/verification.k`, `SCOPE.md`, against
`contract/StandardToken.inlined.sol`, `contract/StandardToken.inlined.bytes`,
and `eip-20.md`.

## Artifacts examined
- `inputs/spec.k` (module `TRANSFER-SPEC`, 5 claims)
- `inputs/verification.k` (`VERIFICATION-SUMMARIES` + `VERIFICATION`)
- `SCOPE.md`

## Mechanical check
- `kprover validate --session 5acb1515-… --spec inputs/spec.k --spec-module
  TRANSFER-SPEC --verification inputs/verification.k --verification-module
  VERIFICATION` → `valid: True`, exit 0 (validation-003). Parses; identifiers
  (`ACCTID`, `CALLER_ID`, `TO`, `VALUE`, `BAL_FROM`, `BAL_TO`, `ACCT_STORAGE`,
  `LOGS`, `CALL_VALUE`) parse as variables, not opcodes (an earlier draft using
  `CALLER`/`CALLVALUE` was rejected because those are EVM opcode tokens — fixed).

## Summary faithfulness
`VERIFICATION-SUMMARIES` defines **no** summary function: `transfer` is
loop-free, so postconditions are stated directly over configuration cells. The
module holds only `StandardTokenRuntime`, a nullary function that expands to
`#parseByteStack("0x…")` of the runtime bytecode. Checked byte-for-byte against
`contract/StandardToken.inlined.bytes` (2091 bytes; generated by a script that
reads that file verbatim). No unfaithful equation exists to hand-evaluate.

## Adequacy (Gate B)

**B1 input-domain alignment.** Storage slot for `balances` is 1 (source order:
`totalSupply`=0, `balances`=1, `allowed`=2; confirmed by the bytecode's
`6001…SLOAD` mapping accesses). `balances[A] = #hashedLocation("Solidity",1,A)`.
The five claims partition the reachable behaviour of the `transfer` selector:

| Claim | Guard restated in plain language | Source branch |
|---|---|---|
| `transfer-success` | `to≠caller`, `value>0`, `bal[caller]≥value`, `bal[to]+value<2²⁵⁶` | if-branch, no wrap |
| `transfer-overflow` | `to≠caller`, `value>0`, `bal[caller]≥value`, `bal[to]+value≥2²⁵⁶` | if-branch, wrap |
| `transfer-self` | `to=caller`, `value>0`, `bal[caller]≥value` | if-branch, same slot |
| `transfer-insufficient` | `bal[caller]<value` | else-branch (returns false) |
| `transfer-not-payable` | `callValue>0` | dispatcher payable guard |

`success`+`overflow` together cover the whole `to≠caller ∧ value>0 ∧
bal[caller]≥value` domain (partitioned on the wrap predicate) — no gap between
them. These are exactly the five properties the task enumerates.

**Recorded exclusions (stated, not silent):**
- `value==0` (with `bal[caller]≥0`) hits the `else` branch and returns `false`
  because the guard is `value>0`. This is a deviation from EIP-20's "transfers
  of 0 MUST be treated as normal transfers", and is **not** among the five
  requested properties; it is left out of the positive theorem deliberately.
  (`transfer-insufficient` requires `bal<value`, which already forces
  `value>0`, so that branch is reached cleanly and does not depend on this.)
- Cross-contract effects, other selectors, and constructor code are out of
  scope by the task ("transfer only").

**B2 model adequacy.** KEVM ISTANBUL, `useGas=true` with symbolic `#gas`.
Numeric wrap is modelled exactly by `chop` (mod 2²⁵⁶) — matching 0.4.x unchecked
`ADD`/`SUB`; the overflow claim's RHS uses `chop(BAL_TO+VALUE)`, the faithful
form. No model boundary is asserted without witness.

**B3/keccak trust boundary.** `transfer-success` and `transfer-overflow` carry
the precondition `#hashedLocation("Solidity",1,CALLER_ID) =/=Int
#hashedLocation("Solidity",1,TO)`. KEVM models `keccak` as an uninterpreted SMT
function with no injectivity axiom, so `CALLER_ID≠TO` alone does not entail slot
distinctness. This is the standard keccak collision-resistance assumption; it is
recorded in `SCOPE.md` and must be carried into the proof's Gate C trust ledger.
The `self` and `insufficient` and `not-payable` claims do not depend on it.

**B4 implementation-vs-intent.** The theorem describes what the code does
(return false on low balance rather than revert; silent recipient overflow;
reject `value==0`). Where that conflicts with EIP-20 SHOULDs, `SCOPE.md`
reports the implementation/spec discrepancy rather than asserting EIP-20
compliance. No claim asserts behaviour the program lacks.

## Findings
None rising to FAIL. The keccak disequality assumption and the `value==0`
exclusion are disclosed in `SCOPE.md`; both are legitimate, witnessed readings,
carried forward for the proof auditor's Gate C.

```text
VERDICT: PASS
REASON: The five claims faithfully and completely state the requested transfer properties over the bytecode, with the keccak-distinctness assumption and value==0 exclusion explicitly recorded.
```
