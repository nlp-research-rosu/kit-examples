## Adequacy (Gate B) — per claim, formal vs source
Restated preconditions/postconditions vs `StandardToken.sol` `transfer` and the
bytecode (BYTECODE-ANALYSIS.md):

1. **transfer-success** — pre: `MSG_SENDER≠TO`, `VALUE>0`, `BAL_FROM≥VALUE`,
   `BAL_TO+VALUE<2^256`; post: `balances[sender]-=VALUE`, `balances[to]+=VALUE`,
   `output=#buf(32,1)`, one Transfer log, SUCCESS. Matches source lines 97–105.
2. **transfer-self** — `TO==MSG_SENDER`, `VALUE>0`, `BAL_FROM≥VALUE`; balances-slot
   entry unchanged, `#buf(32,1)`, Transfer(sender,sender,value), SUCCESS. Matches the
   read-after-write net-zero effect on the shared slot.
3. **transfer-insufficient** — `BAL_FROM<VALUE`; `output=#buf(32,0)`, storage unchanged,
   log unchanged, **SUCCESS (normal RETURN, not revert)**. Matches source `else return false`
   and bytecode false branch at `0x76d`. Contract reading recorded in SCOPE.md.
4. **transfer-not-payable** — `VAL_SENT>0`; REVERT, empty output, storage/log unchanged.
   Matches the non-payable guard `CALLVALUE;ISZERO;JUMPI` at pc `0x193`.
5. **transfer-overflow** — `MSG_SENDER≠TO`, `VALUE>0`, `BAL_FROM≥VALUE`,
   `BAL_TO+VALUE≥2^256`; `balances[to]=BAL_TO+VALUE-2^256`, still `#buf(32,1)`+log, SUCCESS.
   Matches unchecked `ADD` at pc `0x6f7` (Solidity 0.4.x, no SafeMath). This is a
   faithful **B4 implementation/spec discrepancy**: EIP-20 intends value transfer, the
   code silently truncates on recipient overflow; the claim states the program's true
   behaviour, not the EIP intent.

Domain: the task fixes these five cases as the target theorem (not full-domain
coverage of transfer). The five guards partition the requested behaviours without
overlap; each net effect is stated exactly. `VALUE==0 ∧ BAL_FROM≥0` (the other else
trigger) is deliberately outside claim 3's "insufficient balance" reading — recorded
in SCOPE.md, not silent.

## Model boundary / trust
- Environment: ISTANBUL, infinite gas, non-static call — recorded in SCOPE.md; all
  transfer opcodes exist under ISTANBUL. Not a domain narrowing of the program's
  own inputs; a stated execution-model choice.
- **keccak collision-resistance** (claims 1,5): the precondition
  `#hashedLocation("Solidity",1,MSG_SENDER) =/=Int #hashedLocation("Solidity",1,TO)`
  is supplied alongside `MSG_SENDER =/=Int TO`. Justified by keccak injectivity on the
  64-byte pre-images; KEVM models keccak as an uninterpreted total function, so the
  fact is assumed, not derived. Standard EVM storage-aliasing assumption; recorded in
  SCOPE.md and to be carried into the proof trust ledger.

## Evidence gaps (not failures — no divergence witness exists)
- Log topic ordering `[topic0, sender, to]` and success/failure output encodings
  (`#buf(32,1)`/`#buf(32,0)`) are derived from disassembly, not yet from execution.
  No counter-witness is known; the proving stage's symbolic execution is the witness
  that closes this gap. If a residual shows a mismatch, it is a writing-spec repair.

## Verdict

VERDICT: PASS
REASON: The five claims faithfully and structurally match the transfer bytecode and
the task's requested cases; validation compiles clean; the only assumption (keccak
collision-resistance) and the environment are recorded for the trust ledger.
