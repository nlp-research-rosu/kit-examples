# Verification scope

- **Program boundary:** one direct invocation of the exact `run` code object embedded in `/app/program.kpyc`, beginning at bytecode dispatch with two already-bound arguments and ending at the semantics' terminal normal-exit state. Module import/initialization and caller-side argument binding are excluded; the theorem executes every instruction in `run` under the pinned semantics.
- **Input domain:** `a` and `res` are arbitrary mathematical integers represented as Python `int` objects. There are no guards or magnitude bounds. The initial `res` value is arbitrary because the function overwrites it on both branches.
- **Observable final state:** normal exit, final local bindings, and the complete object-memory/allocator update, including the two-element return tuple retained in the heap after the terminal rule consumes its stack pointer. The tuple's first object is the original `a` binding and its second integer value is the computed absolute value. Unrelated runtime cells are unobserved; stdout/stderr are framed because this function performs no I/O.
- **Intended property:** after termination, `a` is unchanged and `res` equals `-a` when `a < 0`, otherwise `a`; equivalently, final `(a, res)` is `(a, abs(a))`.
- **Chosen contract readings:** “integer state bindings” means the full unbounded Python-integer domain modeled by K. “return final `(a, res)`” constrains both tuple components. Direct function entry is used because the supplied image defines but does not invoke `run`, and this bundled semantics supports proof tasks but not concrete-run tasks; the claim observes the exact tuple object left in memory by `BUILD_TUPLE` when top-level `RETURN_VALUE` reaches `#normalExit`.
